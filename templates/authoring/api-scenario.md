# 接口业务场景生成契约

每个业务场景是一条可独立执行的 pytest 测试。不要拆成依赖执行顺序的多个 test。
先输出步骤依据：操作、前置状态、输入来源、提取字段、当前步骤预期、最终状态。

- 用 Service 表达业务动作，fixture 准备当前场景的数据和角色。
- ID/Token 用局部变量或 function fixture 传递，禁止共享 extract.yaml 或跨测试全局变量。
- 每个关键步骤验证状态码与业务状态；最终查询确认业务持久化结果。
- 异步状态使用有超时的条件轮询，不用固定 sleep 猜测完成时间；需要轮询时先复用
  项目能力，缺少明确状态契约则列为待确认，不能无限重试。
- 依赖第三方、队列、定时任务时说明可控触发条件和证据缺口。
- 清理只处理本场景创建的数据，无法回退的业务步骤不能伪造 delete 清理。
- tests/api/<name>/ 中组织场景与 fixture；pytest.mark.api + regression。
- 角色使用 role_clients，业务数据优先复用项目工厂；data_factory 按登记逆序清理，
  每个回调须检查删除/回退结果，失败不能吞掉。没有清理能力的接口记录为未解决项。
- 每条场景用 pytest.mark.case 记录唯一 ID、目的、具体预期和材料来源。
  同一场景内允许多步断言；元数据不得把源码行为冒充需求认可。
- 对准备、关键业务动作、最终核对使用 `log_step` fixture 记录阶段和耗时；不要包装每次请求，
  不把密码、Token、完整请求/响应正文或个人隐私作为步骤参数。

用 tests/api/test_items.py 的创建→查询→删除作为简单参考，复杂业务依据材料生成。
